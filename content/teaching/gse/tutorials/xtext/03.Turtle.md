Our second Domain-Specific Language (DSL) is a simple language for controlling a turtle-like robot. The language allows us to move the turtle forward and backward on a screen and turn it by a certain angle left or right. For directions we use Xtext's enumerations, to group the statements, we use Xtext's interfaces, and to define and reference routines, we use a new feature: Xtext's references.

We will again implement a code generator for our DSL, but this time we will generate JavaScript code that can be executed in a web browser.

To try out the generated JavaScript code, we provide an <a href="../03.turtle/simulation/" target="_blank">executable turtle simulator</a> (similar to the one from the [Blockly tutorial](../../blockly)). You can copy and paste the generated JavaScript code there and see the simulation execute.

## Turtle DSL Example and Grammar

This project overview refers to folder `03.turtle` in the [code examples repository](https://github.com/se-buw/xtext-intro/tree/main/03.turtle).

We create a new Xtext project `org.xtext.example.turtle` with language name `org.xtext.example.turtle.Turtle` and extension `turtle`. We keep all other settings at their default values.

### Example of a Turtle DSL Program

Our language consists of statements for moving and turning the turtle as shown in the example below, which would make the turtle draw a square:

```
move forward 50px

turn right 90 degrees
move forward 50px

turn left 270 degrees
move forward 50px

turn left 90 degrees
move backward 50px
```
Note that this is not the most obvious way to draw a square, but it allows us to use all the statements of our language, i.e., moving `forward` and `backward` and turning `left` and `right`. 

We can also define routines in our DSL to reuse code. For example, we could define a routine `segment` that contains the statements for drawing a segment including the move and turn commands, and then call this routine four times in our main program:

```
routine segment{
	move forward 50px
	turn right 90 degrees
}

run segment
run segment
run segment
run segment
```

### Grammar of the Turtle DSL

We start our implementation by defining the grammar of our DSL in the file `Turtle.xtext`. The grammar defines the structure of models written in our DSL and also serves as a basis for generating an editor for our DSL.

The main two elements of our language are routine definitions and statements. Statements include moving, turning, and calling routines. We define the top-level structure of our models with the `Model` rule, contains zero or more `Routine`s followed by zero or more `Statement`s:

Statements are either `Move`, `Turn`, or `Call` statements. We use an interface `Statement` to group these three types of statements together, which allows us to have a list of statements in the `Model` rule without having to specify the exact type of each statement. 

The rules for `Move` and `Turn` statements are quite straightforward. For moving, we specify the direction as an enumeration (`forward` or `backward`) and the distance in pixels as an `INT` followed by `px`. For turning, we specify the side as an enumeration (`left` or `right`) and the angle in degrees as an `INT` followed by `degrees`.

We will discuss the third type of statement, `Call`, a bit later, first we see how to define routines. A routine consists of the keyword `routine` followed by the name of the routine, which is an identifier of type `ID`, and then a body between curly braces `{}`. The body contains a list of statements, which we can specify as a list of `Statement`s. This way we can have any combination of move, turn, and call statements in the body of a routine:

Finally, to call a routine, we use a `Call` statement, which consists of the keyword `run` followed by a *reference* to a routine. To denote a reference in Xtext, we use a regular attribue (here `routine`) and assign it a reference value by enclosing the type of element we want to reference in square brackets `[]`, i.e., `routing=[Routine]`. 

{{< sub-code

  lang="xtext"

Note that writing `routine=[Routine]` in the grammar would mean something entirely different. We then have to create a new routing for each call statement and could never reuse routine definitions. By writing `routine=[Routine]` we tell Xtext that the value of the `routine` attribute is a reference to an existing routine defined somewhere else in the model. 

In a model we want to use a name to reference a corresponding routine. Thus, Xtext needs some mechanism to resolve the names based on the reference definition. The default mechanism is that Xtext will look for an element of type `Routine` with a `name` attribute that matches the name referenced in the `Call` statement. If you ever want to reference an element without a `name=ID` attribute, you can implement a custom linking mechanism (see [Cross-References](https://eclipse.dev/Xtext/documentation/301_grammarlanguage.html#cross-references) and [Linking](https://eclipse.dev/Xtext/documentation/303_runtime_concepts.html#linking) in the Xtext documentation).

## Meta-Model of the Turtle DSL

To understand the structure of the models we are working with, it is useful to inspect the abstract syntax and meta-model of our DSL as a class diagram. The abstract syntax defines the structure of models in terms of classes and their relationships. The meta-model is a more representation of the abstract syntax used by Xtext for parsing and code generation.

Eclipse Ecore can create a class diagram from the Ecore meta-model generated by Xtext. To do this, we need to locate the Ecore file generated by Xtext for our DSL. This file is located in the `model/generated` folder of the main project `org.xtext.example.turtle` and is named `Turtle.ecore`. 

We can right-click the `Turtle.ecore` file and select `Initialize Ecore Diagram` to create a class diagram from the Ecore meta-model. This will open a wizard and later a new editor for the class diagram. Follow the steps in the video to visualize the class diagram, as shown below.

## Code Generation to JavaScript

We use an <a href="../03.turtle/simulation/" target="_blank">executable turtle simulator</a> that provides as API the following JavaScript functions to control the turtle:
- `move(distance)`: moves the turtle by the given distance in pixels (positive for forward, negative for backward)
- `turn(angle)`: turns the turtle by the given angle in degrees (positive for left, negative for right)

You can copy and paste generated JavaScript code there and see the simulation execute.

### Code Generation Examples
Recall our first example of a program in our DSL for drawing a square:

```
move forward 50px

turn right 90 degrees
move forward 50px

turn left 270 degrees
move forward 50px

turn left 90 degrees
move backward 50px
```

The gap between the statements in the DSL and the API is quite common for code generation, as the DSL is often designed to be more user-friendly and domain-specific than the target code. The code generator will need to bridge this gap and generate the corresponding JavaScript code:

```javascript
turtle.move(50);
turtle.turn(90);
turtle.move(50);
turtle.turn(-270);
turtle.move(50);
turtle.turn(-90);
turtle.move(-50);
```

Our second example program used a routine for drawing a segment:

```
routine segment{
	move forward 50px
	turn right 90 degrees
}

run segment
run segment
run segment
run segment
```

Our code generator would have to generate a JavaScript function for the routine definition and then call this function four times in the main program, as shown below:

```javascript
function segment() {
	turtle.move(50);
	turtle.turn(90);
}
segment();
segment();
segment();
segment();
```

### Code Generation Implementation

We again use Xtend to implement the code generator in the existing file `TurtleGenerator.xtend`. The main method of the generator is `doGenerate`, which is called for each model to be transformed. It takes the root element `resource.contents.head`, which is a `Model` object, and a `fileSystemAccess` object that can be used to write the generated code to a file.

We use the name of the model file as the base for the generated file name. We use `resource.URI.lastSegment` to get the last segment of the URI of the resource, which is the name of the model file. We add the additional extension `.txt`: if the filename is `square.turtle` the generated file will be `/src-gen/square.turtle.txt` regardless of the folder that file `square.turtle` is located in. Below, we also add a first line comment to every generated file that contains the URL of the turtle simulator, so that users can easily find the simulator to try out the generated code:

The code generation for `Move` and `Turn` statements is quite straightforward, as we can directly map the attributes of these statements to the corresponding API calls of the turtle simulator. We the `?` operator of Xtend to check for the direction and we negate the pixel value if the direction is backward. Note that we do negation by simply generating the minus sign: `«m.dir===Direction.BACKWARD?"-":""»`. We handle `Turn` statements in a similar way and add negation to the degree value if the side is `left`: `«t.side===Side.LEFT?"-":""»`.

For routine definitions, we generate a JavaScript function with the name of the routine and the body of the function contains the generated code for the statements in the body of the routine. For routine calls, we generate a call to the corresponding JavaScript function.
